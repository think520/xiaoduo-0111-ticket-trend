## 1. 技术选型与理由

| 决策 | 选择 | 理由 | 被否方案 |
|---|---|---|---|
| 语言 | Python 3.9+（实测 3.12/3.13） | 评审环境大概率有 Python；`uv run analyze.py` 可零配置运行 | Node.js（本机有 v24，但数据分析场景对评审不通用） |
| 依赖 | **仅标准库**（json / statistics / math / datetime / argparse …） | 评审方无需装包；无网络也能跑；结果可复现 | pandas+matplotlib（图表更省事，但要联网装包，评审可能失败） |
| 图表 | 手写 SVG 字符串 | 矢量、可嵌 Markdown/PPT、无字体依赖、无需二进制图片 | matplotlib PNG（依赖重）、ECharts（需联网 CDN） |
| 报告 | Markdown（主）+ 自包含 HTML（展示） | Markdown 便于 diff 与评审；HTML 便于截图与演示 | 只用 HTML（不易 diff）、只用 Markdown（图表需外链） |
| 语义分组 | 规则簇 + Jaccard 相似度 | 确定性、可审计、零成本 | LLM 聚类（运行时依赖 API、不可复现；列入演进路线） |
| 统计 | 描述统计 + 泊松/二项尾部概率（辅助） | 小样本下宁可保守，不做假装严谨的显著性检验 | t 检验/p 值（假设不成立，n=50、存在自相关） |
| 结构 | 单文件 `analyze.py`（约 700 行）+ `unittest` 测试 | 交付物越少越不容易出错；单文件即可 import 也可 CLI | 多模块包（对当前规模是过度设计） |

**约束**：运行时不得联网、不得写工程目录外的文件、不得依赖当前工作目录（用 `__file__` 定位默认输入）。

## 5. 关键算法与口径

### 5.1 通用口径

| 指标 | 公式 | 说明 |
|---|---|---|
| 日均 | `n / 天数` | 前后半段天数不等，必须用日均比较 |
| 占比 | `n_c / N` | 报告统一保留 1 位小数百分比 |
| 占比漂移 | `share_late − share_early` | 单位 pp（百分点），比相对倍数更稳 |
| 分位数 | nearest-rank：`sorted[ceil(p·n)−1]` | 小样本不做线性插值，避免给出不存在的"中间值" |
| 低分率 | `#{sat ≤ 2} / #{sat 非空}` | 均值会被高分掩盖，故双指标并列 |
| SLA 超时 | `resolution_hours > sla[priority]`（仅已解决） | 未解决工单走积压口径 |
| 挂起时长 | 未解决工单的 `resolution_hours` | 语义为"已挂起"，见需求 §4.2 |

**第二轮对齐补充的口径**（v1.1）：

| 指标 | 公式 | 说明 |
| --- | --- | --- |
| 滚动环比 | `最近 3 日日均 / 此前 3 日日均 − 1`，±20% 判增长/下降/稳定 | 与商业工单看板的"本周 vs 上周"口径一致；日期不足 6 天时标记"样本不足" |
| 全量口径分位数 | `percentile_linear()`：线性插值 `v_lo + (v_hi − v_lo)·(pos − lo)`，`pos = (n−1)·p` | 与 Excel / numpy 默认算法一致，用于和外部看板对齐；主口径仍是 `percentile()` 的 nearest-rank |
| 全量口径均值 | 含未解决工单的 `resolution_time_hours`（已挂起时长） | 解决"同一份数据两个数"的沟通问题：本数据 = 19.69h（主口径 13.01h） |
| 时段分布 | 按 `created_at.hour` 分 24 桶计数，取 Top 3 为高峰 | 服务排班；小时粒度样本小，报告与图表均标注"仅参考" |

### 5.2 前后半段划分

```
days = 排序后的去重日期（11 天）
split = len(days) // 2          # 5
early = days[:split]            # 06-01 ~ 06-05（5 天）
late  = days[split:]            # 06-06 ~ 06-11（6 天）
```

用日均而非总量，避免 5 天 vs 6 天直接比总量产生的系统性偏差。`--split-ratio` 可覆盖（默认 0.5）。

### 5.3 复发簇检测（D8 / S2）

三步，全部确定性：

1. **规则命中**：6 组规则，按优先级顺序匹配（一个工单可命中多组，但只归属第一组，避免重复计数；多命中会被记录并在报告脚注披露）：

| 优先级 | key | 名称 | 关键词（任一命中） | 本数据集命中 |
|---|---|---|---|---:|
| 1 | `pay_state_mismatch` | 支付-扣款与订单状态不一致 | 扣了两次 / 重复扣款 / 扣了钱 / 扣钱了 / 已经扣款 / 扣款成功 / 付款成功 / 支付成功 / 待支付 / 未支付 / 没生成 / 订单没成功 / 多扣 / 扣款金额不对 | 12 |
| 2 | `pay_link_failure` | 支付-链路失败与页面异常 | 支付提示失败 / 付不了款 / 一直转圈 / 结算页面打不开 / 付款页面 | 3 |
| 3 | `policy_dispute` | 售后规则争议 | 自动确认收货 / 无理由 / 凭什么 / 不给退 | 2 |
| 4 | `refund_shipping_fee` | 退货运费争议与报销未兑现 | 运费 / 快递费 | 4 |
| 5 | `refund_delay` | 退款/退货到账与审核超期 | 还在审核 / 还在处理 / 钱还没退 / 还没退 / 什么时候退 / 什么时候给 / 不想退 | 3 |
| 6 | `service_experience` | 客服体验（态度/等待/机器人） | 机器人 / 客服态度 / 问了 / 等了 / 人手不够 / 重新描述 | 4 |
| 7 | `account_security` | 账号与安全风险 | 冻结 / 别人用我的账号 / 不是我操作 / 被盗 | 2 |
| 8 | `shipping_delay` | 发货延迟 | 没发货 / 未发货 / 发不了货 | 1 |
| 9 | `logistics_tracking_stuck` | 物流信息停滞 | 没有物流 / 任何物流 / 物流更新 / 没更新 / 快递显示异常 / 物流信息 | 3 |
| 10 | `logistics_delivery_abnormal` | 收货/派送/退件异常 | 被退回 / 签收 / 派送 / 收货地址 / 没收到 / 快递员 | 4 |

2. **一致性（cohesion）**：簇内两两文本的 **Jaccard 相似度**（字符二元组集合，去标点与空白）取平均，再除以**全库随机配对的平均相似度（基准 0.0092）**，得到"相对倍数"。理由是中文短文本的绝对相似度普遍很低（本数据集最高也只有 0.086），用绝对阈值会误判；用相对倍数能回答"簇内是否比随便抽两条更像"。判定：≥2 倍 = 同源佐证；1–2 倍 = 一致性偏弱；<1 倍 = 规则把不同问题混装，降级为"候选簇（观察）"。

3. **复发词**：描述中出现 `又 / 还是 / 一直 / 上个月 / 反复 / 再次` 的条数，作为"这不是第一次发生"的直接证据。

### 5.4 辅助概率校验

```
泊松尾部：P(X ≥ k) = 1 − Σ_{i<k} e^{−λ}·λ^i/i!        λ = 前半段日均 × 后半段天数
二项尾部：P(X ≥ k) = Σ_{i≥k} C(n,i)·p^i·(1−p)^{n−i}   p = 前半段高优占比，n = 后半段条数
```

用 `math.lgamma` / 迭代累乘实现，避免大数溢出。**输出规范**：概率 < 1e-3 表述为"极小（<0.1%）"；1e-3~0.05 表述为"较小"；>0.05 表述为"不能排除随机波动"，且此类信号不允许评为"高危"。

### 5.5 异常打分（S1–S6 → 高危/关注/观察）

按需求 §6.3 的 4 维打分（影响面 0–2、持续/复发 0–2、严重度 0–2、体验 0–2），求和 0–6 后映射分级；**S5 积压**（绝对量事实）固定为高危，**S6 渠道差异**固定为关注，因为它们不需要概率论证。

三条去重/保守规则（都在代码里可查）：

1. **S1 + S2 合并**：若某分类的突增信号与该分类内最大簇同源，合并为一条异常（`type: ["S1","S2"]`），保留最高分。
2. **S3 + S4 合并**：同一分类同时是效率堵点与体验塌陷时合并为"效率与体验双差"，避免同一件事出现两次。
3. **小样本与一致性守卫**：条数 < 5 不得评为高危；尾部概率 > 0.05 不得评为高危；簇内一致性低于全库随机配对时降级为"候选簇（观察）"。

同级别内的排序：变化类信号（S1/S2）优先于状态类信号（S3–S6），再按分值、影响面（条数）排序 —— 让"刚发生的变化"排在"长期状态"前面。

### 5.6 工单级优先清单（第二层输出）

信号级异常之后，再对每张工单算一个跟进分值（`rank_tickets()`）：

```
score = 3·[未解决] + 1·[未解决且挂起超 SLA] + 2·[高优先级] + 1·[中优先级]
      + 2·[耗时/挂起 ≥ 全量口径 P90] + 2·[满意度 ≤ 2] + 1·[命中复发簇]
```

分级：`P1 ≥ 9`（今天处理）、`P2 7–8`（本周跟进）、`P3 5–6`（备查，报告里只列工单号），`< 5` 不进清单。
阈值按本数据集的分值分布标定：11/11/11/9/9 ｜ 8/8/7/7/7 ｜ 5×13，8 与 7 之间存在断层，因此 P1 卡在 9 分。
实现细节：`p90` 取自**全量口径**（含未解决工单），保证"挂起很久"的未解决工单也能被 P90 条件捕获；输出里每条都带 `reasons[]`，报告与 Dashboard 会原样展示命中原因，并声明"非企业正式事故等级"。

## 6. 命令行接口

```bash
# 默认：读 task5_tickets.json，写 output/
uv run analyze.py

# 指定输入输出与 SLA
uv run analyze.py --input data/tickets.json --outdir out --sla 高=12,中=24,低=48

# 只输出某一类产物
uv run analyze.py --formats md,json
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--input` | 脚本同目录 `task5_tickets.json` | 支持 `.json` 数组，或 `.csv`（表头同上） |
| `--outdir` | `output` | 产物目录，自动创建 |
| `--formats` | `md,html,json,charts` | 逗号分隔 |
| `--sla` | `高=24,中=48,低=72` | 覆盖 SLA 假设 |
| `--split-ratio` | `0.5` | 前后半段切分比例 |
| `--min-cluster` | `3` | 簇进入异常候选的最小条数 |
| `--strict` | 关 | 严格校验：字段类型/取值不合契约时直接报错退出（退出码 1）；默认宽松告警并继续 |
| `--quiet` | 关 | 只输出错误 |
| `--version` | — | 打印版本 |

退出码：`0` 正常；`1` 输入不可读/格式错误；`2` 参数错误。**stdout 打印可读摘要**（总数、分级计数、产物路径），便于截图与 CI。

## 7. 渲染层

### 7.1 Markdown（`趋势分析报告.md`）

章节顺序：摘要（6 条结论）→ 数据质量 → D1–D8 维度（每节：结论一句话 + 表格 + 图表引用）→ 异常清单（按分级排序，每条含证据/依据/动作/复核）→ 方法与阈值 → 局限性 → 附录（指标字典、簇规则表、多命中工单）。

### 7.2 HTML Dashboard（`dashboard.html`）

- **自包含**：CSS 与 SVG 内联，无 CDN、无外部字体、**无任何 JavaScript**。断网双击即可打开，可直接截图或打印成 PDF。
- **布局**：顶部 **KPI 条**（同级数据共用一个 band + 1px 细分隔线，而不是 N 张卡片）→ 6 张图表（每张下面一句**结论式图注**，写"所以呢"而不是"画了什么"）→ 复发簇与积压表 → 异常卡（高危深蓝 / 关注橄榄 / 观察灰，左侧 3px 色条区分）→ 工单级优先清单 → 分类明细表 → 方法与局限脚注。
- **视觉语言（kami 设计规范）**：暖羊皮纸底 `#f5f4ed`、卡片象牙白 `#faf9f5`、**唯一强调色 ink blue `#1B365D`**，其余全部为暖灰阶（`#504e49` / `#6b6a64` / `#b8b7b0` / `#d4d3cd`）；细线分隔、无投影、无渐变、图例画在绘图区之外并用细线分隔；SVG 画布带羊皮纸点纹（每个图的 pattern id 唯一，避免同页 6 张 SVG 冲突）；数值标签一律画在**羊皮纸色遮罩矩形**上，避免网格线/日均线从字里穿过。图表调色板取自 kami 数据图表 6 序列定义，全部为实心色（不用 `rgba()`）。
- **字体（内嵌，零外链）**：字体栈为 `"TsangerJinKai02" → "Kami Serif" → Charter/Georgia → Source Han Serif → Noto Serif CJK/SC → Songti → serif`。其中 `Kami Serif` 是 `assets/fonts/NotoSerifSC-subset.woff2`（Noto Serif SC 可变字重子集，OFL 许可，按本页 646 个字符子集化，243KB），`Kami Mono` 是 JetBrains Mono 子集（同 OFL）；两者由 `font_face_css()` 以 `data:font/woff2;base64` 内嵌进 HTML，因此线上 Demo 与本地离线字形一致，且**不产生任何外部字体请求**。字体文件缺失时自动跳过内嵌并回退系统衬线（CI 友好）。子集化步骤见 `assets/fonts/README.md`。
- **可读性**：中文文案；图表标注数值与单位；正文页填充率 ≥60%；异常卡与表格 `break-inside: avoid`。
- **响应式**：≤880px 时 KPI 条降为 3 列、≤480px 降为 2 列；宽表格放入 `overflow-x:auto` 的容器；图表容器给 `min-width:620px` 并允许横向滑动，**不把 860 宽的图缩成不可读字号**。已在 375px 与 1280px 两个宽度用 Edge headless 实测截图核对。

## 8. 容错与数据质量

| 场景 | 处理 |
|---|---|
| 文件不存在 / JSON 解析失败 | 打印可读错误 + 退出码 1 |
| 缺字段 | 记入 `warnings`，缺失分类 → "未分类"，缺失满意度 → 从满意度分母剔除 |
| 未知优先级 | 归为"未标注"，不计入 SLA 判定，并告警 |
| 未知渠道 | 保留原值参与分布，并告警（本数据集缺失"邮件"渠道 → 提示字段说明与数据不一致） |
| 时间格式错误 | 记入 `warnings` 并跳过该条（不静默改动时间） |
| 重复 `ticket_id` | 去重保留首条 + 告警 |
| 数值越界（满意度不在 1–5 / 时长 < 0） | 告警并置空，不参与对应统计 |
| 空数据 | 输出"无数据"报告骨架，退出码 0（不算错误，避免调度系统误报） |

## 10. 已知局限与改进方向

1. **聚类靠规则**：召回受同义词限制，报告显式给出"未归类工单数"作为召回缺口的代理指标；下一步用句向量聚类（保留规则簇做兜底）。
   - 已设计但**本期不实现**的可选方案（`--llm`，默认关闭）：① `/v1/embeddings` 取 `text-embedding-3-small` 向量，用余弦相似度 + 公开阈值（默认 0.60）做贪心聚簇，只输出 ≥3 条的簇，并与关键词簇做差集对照（"只有语义簇抓到"= 关键词漏检）；② 用 Responses/Chat Completions 生成 3 条行动建议，报告里标注"本段由 LLM 生成 + 模型名 + 输入摘要 + 生成时间"；③ 无 `OPENAI_API_KEY` 或网络失败时自动降级为纯规则路径并在报告里写明原因。放弃原因见 README「为什么工具内不接 LLM」。
2. **无历史基线**：11 天窗口只能做窗口内对比，无法区分季节性；需要 90 天数据。
3. **优先级/分类由人工录入**：口径漂移会污染趋势判断（例如新人不熟悉分类）。建议在报告脚注提示"分类变更需同步"。
4. **SLA 是假设值**：所有超时类结论都可被 `--sla` 重算，避免把假设当事实。
5. **概率校验的边界**：泊松/二项假设独立同分布，工单存在自相关，故只作辅助证据；不做多重比较校正，只对通过初筛的信号计算。
