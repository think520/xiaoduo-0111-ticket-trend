# 换数据集指南（用别的工单数据跑同一套分析）

> 结论先说：**换数据集不需要改代码**，只需要换 `--input`。
> 本文覆盖：怎么换、字段要求、换完怎么体检、什么情况下必须改配置、以及三个最容易踩的坑。

---

## 1. 三种换法（都实测过）

```bash
# ① JSON 数组（与 task5 同字段名）
uv run analyze.py --input 别的测评集.json --outdir out

# ② CSV（表头用契约字段名；CSV 里所有值都是字符串，工具会自动转换）
uv run analyze.py --input 别的测评集.csv --outdir out

# ③ 中文表头 CSV / 中文列名（内置别名表，例如 工单号/创建时间/分类/问题描述/优先级/处理时长/满意度/渠道/是否已解决）
uv run analyze.py --input 中文表头数据.csv --outdir out

# 顺带可以覆盖业务参数
uv run analyze.py --input 别的.json --sla 高=12,中=24,低=48 --split-ratio 0.4 --outdir out
```

仓库自带一份与 task5 完全不同的小示例（2025-03、24 条、5 个新分类、含"邮件"渠道）：

```bash
uv run analyze.py --input examples/tickets_example.json --outdir out --strict
uv run analyze.py --input examples/tickets_example.csv  --outdir out --strict
```

> 这两个命令也在 CI 里每次推送都跑（`tests.yml` 的"换数据集"步骤），并断言 JSON 与 CSV 得到**完全一致**的指标。

## 2. 数据契约（字段与容错）

| 字段 | 类型 | 必需 | 不满足时工具怎么做 |
| --- | --- | --- | --- |
| `ticket_id` | string | ✅ | 缺失 → 用 `ROWn` 兜底；重复 → 跳过后续并告警 |
| `created_at` | string | ✅ | 只认 `YYYY-MM-DD HH:MM` / `YYYY-MM-DD HH:MM:SS` / `YYYY-MM-DD`；不合规 → **跳过该条**并告警 |
| `category` | string | ✅ | 自由文本；新分类原样参与统计，不做白名单限制 |
| `description` | string | 建议 | 缺失则该条不参与复发簇识别 |
| `priority` | string | ✅ | 见 §4 陷阱①：**默认只认 `高/中/低`** |
| `resolution_time_hours` | number | 建议 | 非数字/负数 → 置空并排除该统计（SLA、分位数） |
| `satisfaction` | number 1–5 | 建议 | 越界/非数字 → 置空并从低分率分母剔除 |
| `channel` | string | 建议 | 未知取值只告警，不影响计算（默认期望 `在线/电话/邮件`） |
| `is_resolved` | bool | ✅ | 认 `true/false`（大小写均可）、`1/0`、`yes/no`、`是/否`、`已解决/未解决`；缺失/无法解析 → 按未解决并告警 |

字段名别名（`analyze.py` 的 `FIELD_ALIASES`，可继续加）：
`ticket_id|id|工单号`、`created_at|created|创建时间`、`category|分类|问题分类`、`description|desc|问题描述`、`priority|优先级`、`resolution_time_hours|resolution_hours|处理时长`、`satisfaction|满意度`、`channel|渠道|来源渠道`、`is_resolved|resolved|是否已解决`。

退出码约定：`0` 正常（含空数组）、`1` 输入不可读/解析失败（含 `--strict` 校验失败）、`2` 参数错误。

## 3. 换完数据集的四步体检

```bash
# ① 契约体检：类型/取值不合规直接报错（CSV 的字符串值会先被解析，不会误报）
uv run analyze.py --input 新数据.json --outdir out --strict

# ② 看"数据质量告警"条数（报告 §1）：日期被跳过、渠道不在枚举、缺满意度等都会列出来
#    以及"未解决工单带处理时长"这类语义提示

# ③ 看报告 D8 的"未归类到任何规则簇的工单 N 条"：
#    N 很大 → 说明新语料的关键词与内置 10 组规则不匹配（见 §4 陷阱③）

# ④ 看 SLA 超时是否为 0：若为 0 且数据里明明有超长工单，多半是优先级词表对不上（陷阱①）
```

## 4. 三个最容易踩的坑（换数据集时必看）

### 陷阱① 优先级词表默认是「高/中/低」

如果新数据用 `P0–P3`、`High/Medium/Low`、`1/2/3`，工具**不会崩**，但会静默失效三处：
**高优先级占比、SLA 超时判定、工单级 P1–P3 评分**（因为比较的是 `priority == "高"`，且 `DEFAULT_SLA` 以 `高/中/低` 为键）。

处置方式（任选）：

- **① 用 `--priority-map`（推荐，无需改代码）**：工具读取时就把外部词表归一化成 `高/中/低`，三处失效全部恢复：

  ```bash
  uv run analyze.py --input 别的测评集.json --outdir out --priority-map "P1=高,P2=中,P3=低"
  # 任意词表都可以：High=高,Medium=中,Low=低   /   1=高,2=中,3=低   /   P0=高,P1=高,P2=中,P3=低
  ```

  映射结果会写进 `metrics.json` 的 `meta.config.priority_map`，报告的数据质量章节也会注明，例如
  "已按 --priority-map 归一化优先级：P1→高（31 条）、P2→中（13 条）、P3→低（6 条）"。
  实测：把 task5 的优先级整体换成 P1/P2/P3 后，**不加映射**→ 高优占比 0%、SLA 超时 0 条、工单级 P1 0 条；
  **加上映射**→ 高优占比 62%、SLA 超时 4 条、工单级 5/5/13，与原始数据**指标完全一致**。
- ② 只用 `--sla P1=4,P2=24,P3=72` 提供 SLA：超时能算，但**高优占比与工单级评分仍会算成 0**，不推荐单独使用；
- ③ 改代码：把 `analyze.py` L38 `EXPECTED_PRIORITIES` 与 L36 `DEFAULT_SLA` 改成新词表，并同步 `compute_metrics` 与 `rank_tickets` 里比较 `"高"/"中"` 的两处（适用于长期固定英文词表的场景）。

### 陷阱② 时间格式只认三种

`2025/03/03 09:00`、`2025-03-03T09:00:00Z` 这类写法会被当成非法时间**跳过该条**（会在告警里逐条列出）。
处置：在 `analyze.py` 的 `_parse_dt()` 里加格式串（一行一个），或先在数据侧统一成 `YYYY-MM-DD HH:MM`。

### 陷阱③ 复发簇的关键词表是业务语料相关的

`CLUSTER_RULES`（`analyze.py` L44）是 10 组中文关键词规则，针对"退款/支付/物流/客服体验"这类电商客服语料。
换到别的语料（例如本次示例的"发票问题、尺码咨询"）后，未归类条数会明显上升——这是**预期行为**，报告会把它显式写出来。
处置：先跑一遍，打开报告附录 B 看规则表，再照"未归类工单"的描述补关键词。

## 5. 换数据集时"必须改代码"的只有 4 个位置

| 位置 | 常量 | 什么时候必须改 |
| --- | --- | --- |
| `analyze.py` L36 | `DEFAULT_SLA` | SLA 口径不同（可先用 `--sla` 覆盖，无需改代码） |
| `analyze.py` L38 / L39 | `EXPECTED_PRIORITIES` / `EXPECTED_CHANNELS` | 优先级/渠道取值集合不同（不改只会告警，但陷阱①会影响结论） |
| `analyze.py` L41 | `RECURRENCE_WORDS` | 复发词不同（英文语料可加 `again/still/repeated`） |
| `analyze.py` L44 | `CLUSTER_RULES` | 语料主题不同 → 未归类比例升高，按需补词 |
| `analyze.py` L358 | `FIELD_ALIASES` | 字段名对不上（一行加一个别名） |

**不需要改的**：日期范围、天数、分类集合、前后半段切分点、日均/占比/漂移、P50/P90、SLA 超时率、时段分布、滚动环比、工单级评分——这些全部由数据推导，没有写死"50 条 / 2026-06 / 支付问题"。

## 6. 规模边界

| 数据量 | 表现 |
| --- | --- |
| ~50 条（本任务） | 瞬时完成（< 0.2s） |
| 数千条 | 可用；簇内一致性是两两比较（`O(n²)`），几十万对仍在秒级 |
| 数万条以上 | 需要改造：先按分类/时间分桶，再在桶内做倒排索引或向量检索，避免全量两两比较（见实现文档 §10「已知局限」） |

另外：文档、报告、Dashboard 的文案与字体子集是按"本页出现的字符"生成的；如果新数据集引入了大量生僻字，`assets/fonts/README.md` 里给了重新子集化的命令（不重做也能跑，个别字会回退系统衬线）。
