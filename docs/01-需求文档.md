## 1. 背景与问题定义

### 1.1 现状

客服主管每天面对工单列表，需要回答三个问题，但目前只能靠人工翻列表：

1. **什么变多了？** —— 哪类问题在最近几天集中爆发，是随机波动还是趋势？
2. **什么最严重？** —— 哪些问题影响面大、超时多、把客户惹毛了？
3. **我该先做什么？** —— 今天/本周最值得投入资源的 1~3 件事是什么？

### 1.2 人工方式的三个失效点

| 失效点 | 具体表现 | 后果 |
|---|---|---|
| 看不全 | 50 条已经看不完，实际业务中每天几百条 | 只看到最近被投诉的那几条，看不到分布 |
| 记不住 | 无法把"上周的退款慢"和"这周又出现"联系起来 | 复发型问题被当成新问题处理 |
| 说不清 | 结论只有"感觉最近支付问题多" | 无法向研发/仓储部门提出有依据的推动 |

### 1.3 本工具要解决的问题

把"翻列表"变成**结构化的趋势报告 + 明确的异常清单**：机器负责算分布、算变化、找复发，主管只负责判断和决策。

**一句话定义**：输入工单数据（JSON/CSV），输出一份能直接用于晨会决策的趋势报告，其中每条异常都附带证据、判断依据、置信度和建议动作。

## 2. 目标与非目标

### 2.1 目标（本期必须做到）

- **G1 覆盖 9 个分析维度**：时间趋势、分类结构、严重程度、处理效率、客户体验、渠道结构、积压状态、关联关系（重复问题簇）、时段分布。
- **G2 输出结构化报告**：Markdown 报告 + 自包含 HTML Dashboard + 机器可读 `metrics.json`。
- **G3 异常可解释**：每条异常必须能回答"凭什么说它异常"，而不是只给一个分数。
- **G4 完全可复现**：零第三方依赖，同一份输入在任何机器上得到完全相同的输出。
- **G5 诚实面对小样本**：样本只有 50 条 / 11 天，明确区分"值得复核的信号"与"统计显著结论"。

### 2.2 非目标（本期明确不做）

| 不做的事 | 原因 |
|---|---|
| 实时告警 / 消息推送 | 主管的决策节奏是每天一次，实时推送会制造噪声；且需要接入工单系统 |
| 直接对接工单系统 API | 需要账号、权限、字段映射，属于集成工作，与本期的分析能力验证无关 |
| 用 LLM 做运行时语义聚类 | 会引入 API Key、成本、不可复现性问题；本期用确定性规则 + 相似度计算替代（见 §6.4） |
| 因果推断（如"因为支付故障导致退款变多"） | 本数据是观察性小样本，无法识别因果；报告只陈述共现与变化 |
| 统计显著性假设检验的完整体系 | n=50、无历史基线、工单本身存在自相关，做严格检验会给出虚假的精确感；只用泊松/二项尾部概率作为**辅助证据** |
| 多租户 / 多语言 / 权限体系 | 无需求场景，属于过度设计 |

## 4. 输入与数据契约

### 4.1 输入

`task5_tickets.json`：50 条工单，时间跨度 2024-06-01 ~ 2024-06-11（11 天），UTF-8 编码的 JSON 数组。

| 字段 | 类型 | 用途 | 质量风险 |
|---|---|---|---|
| `ticket_id` | string | 唯一标识、异常清单里可回溯 | 需查重 |
| `created_at` | string `YYYY-MM-DD HH:MM` | 时间维度、簇的首现与持续天数 | 需解析校验 |
| `category` | string（6 类） | 结构分析主键 | 枚举变化需告警 |
| `description` | string（用户原文） | 复发簇识别、相似度计算 | 无结构化标签，只能靠文本规则 |
| `priority` | string（高/中/低） | 严重程度、SLA 口径 | 枚举需校验 |
| `resolution_time_hours` | number | 处理效率、SLA、堵点识别 | **未解决工单也带数值**，语义需假设（见 §4.2） |
| `satisfaction` | number 1–5 | 客户体验 | 无缺失值，但实际业务中会缺 |
| `channel` | string（在线/电话） | 渠道结构 | **字段说明写了"邮件"，数据中不存在** |
| `is_resolved` | boolean | 积压、SLA 分母口径 | —— |

### 4.2 必须在需求阶段明确的三个语义假设

> 这三条直接影响数字口径，属于"必须先定、不能后补"的决定。

1. **未解决工单的 `resolution_time_hours` 视为"已挂起时长"**，而不是"最终处理时长"。
   → 因此 SLA 达成率**只对已解决工单计算**；未解决工单进入"积压与挂起时长"维度，避免用未完成的时长污染效率指标。
2. **SLA 目标值由本工具假设**：高优先级 24h / 中 48h / 低 72h（可命令行覆盖）。
   理由：这是国内电商客服的常见分级承诺；本数据集没有 SLA 字段，无法从数据推导。**这是本方案唯一需要业务方确认的硬编码参数**，报告与 README 均标注为假设值。
3. **观察窗口内的未解决工单视为持续未关闭**（用于画积压曲线）。
   理由：数据没有关闭时间字段，无法知道期间是否有工单被解决。该假设使积压曲线偏保守（偏高）。

### 4.3 已识别的数据质量问题（工具需报告，不得静默处理）

| 问题 | 现状 | 工具的处理方式 |
|---|---|---|
| 渠道枚举不一致 | 字段说明含"邮件"，实际只有"在线/电话" | 报告"数据质量"章节显式提示，不臆造缺失渠道 |
| 未解决工单带处理时长 | 8 条未解决工单均有数值 | 单独统计，不与已解决口径混算（§4.2-1） |
| 无客户/订单维度 | 无法判断同一客户重复来电、无法关联订单 | 列入局限性，不假装能分析 |
| 无标签、无根因字段 | 只能靠描述文本 | 用关键词规则 + 相似度，并公开规则表供复核 |

## 5. 分析维度设计（核心章节）

**维度取舍原则**：每个维度必须能改变主管的某个具体动作，否则不做。下表 9 个维度全部满足"有明确决策价值 + 本数据能算 + 能画出来"（D9 与 D1 的滚动环比是第二轮按业界看板口径补充的）。

### D1 时间趋势（量在变多还是变少）

- **口径**：每日新增工单数；前半段/后半段日均（`后半日数 = n - ⌊n/2⌋`）；**滚动环比：最近 3 日 vs 此前 3 日，±20% 判增长/下降/稳定**；峰值日；日波动系数 CV = 标准差/均值。
- **决策价值**：决定排班与人力。日量上行 → 需要预排加班或临时支援；出现峰值日 → 复盘当天是否有活动/故障。滚动环比回答"**最近**有没有变"，比整段对半更贴近主管每天看数据的直觉。
- **本数据事实**：3 → 6 条/天缓慢上行；前半 19 条（3.8/天）、后半 31 条（5.2/天），+36%；滚动环比 +6.6% → 判定"稳定"；峰值 06-10（6 条）。
- **局限**：11 天窗口含周末，无法区分"自然增长"与"事件驱动"。

### D2 分类结构（问题集中在哪条业务线）

- **口径**：分类计数与占比；**前后半段占比漂移（百分点 Δpp）**——比总量变化更能说明"结构性问题"。
- **决策价值**：占比漂移是最强的行动信号。总量上升可能是业务量整体上涨，但某类占比翻倍意味着链路出了新问题。
- **本数据事实**：支付问题 16 条（32%），前半占比 15.8% → 后半 41.9%（**+26.1pp**）；退款退货 31.6% → 22.6%（−9.0pp）。
- **局限**：分类由录入人决定，存在归类不一致的可能。

### D3 严重程度（是不是越来越严重）

- **口径**：优先级分布；高优先级占比及其前后半段变化；分类 × 优先级交叉。
- **决策价值**：高优占比上升说明"不只是变多，而是变得更严重"，直接对应升级处理与跨部门协同。
- **本数据事实**：高优先级 31/50（62%）；前半 47.4% → 后半 71.0%（+23.6pp）；支付问题 16 条中 14 条为高优先级。
- **局限**：优先级由客服人工判定，不同人宽严不一；本数据集无人为压低/抬高的证据，但不可排除。

### D4 处理效率（堵在哪一步）

- **口径（双轨）**：**主口径** = 仅已解决工单，P50/P90 用 nearest-rank（小样本不插值）；**全量口径** = 含未解决工单的"已挂起时长"，P90 用线性插值（Excel/numpy 默认）。另计 SLA 超时数与超时率（仅已解决工单）与超时工单号。
- **决策价值**：区分"量大的问题"和"耗时的问题"。量小但耗时极长的分类，往往是需要流程改造的真堵点（会持续消耗人力并拉低满意度）。双口径的价值是**避免与其它看板对不上**：两种算法都合理，差别只来自"未解决的 8 条算不算"。
- **本数据事实**：主口径全局均值 13.0h / P50 6h / P90 24h，退款退货 30.0h；全量口径全局均值 19.7h / P90 50.4h，退款退货 45.2h；全局 SLA 超时 4 条（9.5%），另有 5 条未解决工单挂起时长已超 SLA（最长 T031 已挂 120h）。
- **局限**：处理时长不含客户等待被受理的时间；未解决工单挂起时长可能被低估。

### D5 客户体验（客户到底满不满意）

- **口径**：满意度均值；**低分率（≤2 分）**；按分类、按渠道；按处理时长分桶。
- **决策价值**：满意度是结果指标，用来验证"效率提升有没有变成客户感受"。低分率比均值更敏感（不被高分掩盖）。
- **本数据事实**：均值 2.36，低分率 54%（27/50）；投诉类均值 1.00（4 条全 1 分）；退款退货均值 2.00。
- **局限**：满意度通常存在"不评价偏差"（不满才会填），不能与行业基准直接比较。

### D6 渠道结构（资源该往哪个渠道压）

- **口径**：渠道分布；分渠道的满意度与处理时长对比。
- **决策价值**：同为高优先级，若某渠道用时明显更长，问题就在该渠道的排班或工具支持。
- **本数据事实**：在线 34 条 / 电话 16 条；电话渠道平均处理 18.2h，高于在线的 10.9h（1.7 倍），且满意度更低（1.9 vs 2.6）、低分率更高（75.0% vs 44.1%）。

### D7 积压状态（有多少事没关掉）

- **口径**：每日新增未解决数、累计未解决曲线、挂起时长排序（含高优先级占比）。
- **决策价值**：这是主管最直接的"TODO 清单"。积压里高优先级占比越高，越需要当天介入。
- **本数据事实**：未解决 8 条（16%），其中 7 条是高优先级；5 条属于退款退货；最长挂起 120h（T031）。

### D8 关联关系 / 重复问题簇（同一个根因反复出现）

- **口径**：基于描述文本的**规则簇**（关键词/短语规则表，公开可审）+ 簇内一致性（平均两两 Jaccard 相似度）+ 复发词命中（"又/还是/一直/上个月/反复"）+ 簇的时间跨度和日频次。
- **决策价值**：这是单看分类分布**完全看不到**的信号。同一个类目里可能混着两类问题：一类是正常咨询，一类是同一个系统缺陷在反复出血。簇能把"12 张看似不同的工单"压缩成"1 个根因假设"，这是推动研发排查的关键证据形式。
- **本数据事实**：10 个规则簇共覆盖 38 条工单（未归类 12 条），其中 7 个条数 ≥3 进入异常候选。"支付-扣款与订单状态不一致"12 条、跨 9 天（8 个不同日期）、高优先级 100%、平均满意度 2.00、复发词 2 条，簇内文本相似度是全库随机配对基准的 6.1 倍（0.056 vs 0.0092），是目前最明确的同源问题。
- **局限**：关键词规则会漏掉未被规则覆盖的同义表述（召回不全）；因此报告同时给出"未归类到任何簇的工单数"，把召回缺口显式暴露出来。

### D9 时段分布（人力压在哪个时段）

- **口径**：按创建时间的 24 小时分布；标出工单量最高的三个时段；与峰值日互为补充（一个是"哪天多"，一个是"哪个点忙"）。
- **决策价值**：直接服务排班 —— 主管可以把人力压在 09:00–10:00 与 14:00 前后，而不是平均分配；也能解释"为什么某些时段响应慢"。
- **本数据事实**：高峰 09:00（9 条）、10:00（7 条）、14:00（7 条）。
- **局限**：11 天 / 50 条做小时切分后每格只有 0–9 条，只能作方向性参考，不能作为排班唯一依据。

## 6. 异常信号的定义与分级

### 6.1 异常的定义

> **异常 = 与"业务连续、随机波动"的预期相比，出现方向一致、幅度足够、且能落到具体工单的证据模式。**

关键在于"能落到具体工单"：只报告指标而不给工单号的异常，主管无法行动。

### 6.2 六类信号（按检测目的划分）

| 编号 | 信号类型 | 触发条件（全部可复核） |
|---|---|---|
| S1 | 分类突增 | 后半段日均 ≥ 前半段日均 × 2 且后半段条数 ≥ 5 |
| S2 | 复发簇 | 簇内 ≥ 3 条 且 跨 ≥ 3 个不同日期；簇内文本一致性作为同源佐证（相对全库随机配对 ≥2 倍为强佐证，<1 倍视为规则混装了不同问题 → 降级为"候选簇/观察"） |
| S3 | 效率堵点 | 分类平均处理时长 ≥ 全局平均 × 1.5 且 该分类超时/未解决条数 ≥ 3 |
| S4 | 体验塌陷 | 分类满意度均值 ≤ 2.5 且 低分率 ≥ 60%（样本 ≥ 3 条） |
| S5 | 积压累积 | 未解决 ≥ 5 条 且 其中高优先级占比 ≥ 50% |
| S6 | 渠道差异 | 某渠道平均处理时长 ≥ 另一渠道 × 1.5（样本各 ≥ 5 条） |

### 6.3 分级：把"信号"变成"优先级"

每个命中的信号按 4 个维度打分（总分 0–6），分级输出：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 影响面 | 占比 < 10% | 10%–<20% | ≥ 20% |
| 持续/复发 | 单日 | 跨 2–5 天 | 跨 ≥ 6 天 |
| 严重度 | 高优占比 < 40% | 40%–<60% | ≥ 60% |
| 体验损失 | 均值 > 3.0 | 2.5–3.0 | ≤ 2.5 或低分率 ≥ 50% |

分级规则：**≥ 5 分 = 高危（当天行动）**；**3–4 分 = 关注（本周跟进）**；**≤ 2 分 = 观察（记录，不投入资源）**。
两条保守约束（避免小样本被过度解读）：① 条数 < 5 的信号不得评为高危；② 尾部概率 > 0.05（不能排除随机波动）或簇内一致性低于随机配对时，最高只能评为关注/观察。

### 6.4 辅助证据：小样本下怎么避免"编故事"

规则命中不等于真异常（50 条数据里，随机也可能出现 3 条同类）。因此对 S1/S2 追加两项辅助校验，并在报告中**明示为辅助证据**：

1. **泊松尾部概率**：以观察窗前半段的日均作为基线 λ，计算后半段出现"不少于实际条数"的概率。
   例：支付问题前半段 0.60 条/天，后半段 6 天期望 3.6 条，实际 13 条 → 尾部概率极小（工具会算出具体值，量级 1e-4 以下），说明"这不是随机波动"。
2. **二项尾部概率**：检验高优先级占比变化（前半 47.4% 作为基线，n=31 观察到 22 条高优 → 尾部概率 0.0068，说明占比抬升不太可能纯属偶然）。
3. **簇内一致性**：以全库两两文本相似度（字符二元组 Jaccard 均值 0.0092）为基准，看簇内相似度是否显著更高；本数据集"收货/派送/退件异常"簇只有基准的 0.65 倍，工具因此把它降级为"候选簇（需复核）"，而不是当成同源问题上报。

**局限必须同时声明**：工单到达并非严格独立同分布（存在聚集与自相关）、基线只用 5 天估计、且我们是对多个信号做筛选（多重比较）。因此这些概率只用于**排除明显的偶然**，不作为"统计显著"结论。

### 6.5 异常条目的必备字段

每条异常必须包含：`信号类型 / 分级 / 分值 / 证据（数字） / 涉及工单号 / 判断依据（阈值+概率） / 置信度说明 / 建议动作 / 如何复核`。

### 7.2 工单级优先跟进清单（信号级之外的第二层输出）

信号级异常回答"哪里出问题了"，但主管真正要执行的是一张工单清单。因此对每张工单按下列规则累加打分：

| 命中条件 | 加分 |
| --- | ---: |
| 未解决 | +3 |
| 未解决且挂起时长已超 SLA | +1 |
| 高优先级（中优先级 +1） | +2 |
| 耗时/挂起 ≥ 全量口径 P90 | +2 |
| 满意度 ≤2 | +2 |
| 命中复发簇 | +1 |

分级：**P1 ≥9 分（今天处理）、P2 7–8 分（本周跟进）、P3 5–6 分（备查/顺手处理，只列工单号）**，低于 5 分不进清单。
阈值不拍脑袋：本数据集分数分布在 8 分与 7 分之间有明显断层（11/11/11/9/9 ｜ 8/8/7/7/7 ｜ 5×13），据此把 P1 卡在 9 分，保证 P1 是真正需要人介入的那 5 条。
清单必须带免责声明：**P1/P2/P3 是工具的跟进优先级，不是企业正式事故等级**，避免被当成对外通报口径。

## 8. 验收标准（可执行断言）

16. `--strict` 模式下，字段类型/取值违规（如 `is_resolved: "true"`、优先级"紧急"）直接报错退出（退出码 1）；默认模式仍宽松告警并跑完。
17. 图表共 6 张（含时段分布），全部为可独立打开的 SVG。
